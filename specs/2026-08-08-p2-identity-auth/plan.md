# Plan — P2: Identity for Real

> How [`requirements.md`](./requirements.md) gets built, in commit-sized phases ordered by
> de-risk: the cluster-side plumbing (branch tracking, secrets, credentials, image pull) comes
> before the service rewrite, because a perfect service that cannot start on a fresh cluster fails
> the exam's opening move — and because without branch tracking no drill can test P2's own code.
> Design decisions are the implementer's (D-n) — flag objections early, they harden as they ship.

## Design decisions (confirm in review)

- **D1 — Password hashing with `node:crypto` scrypt** (N=16384, r=8, p=1, 16-byte salt, 64-byte
  key), stored as `scrypt$N$r$p$salt$hash` and compared with `timingSafeEqual`. argon2id rejected:
  it is a native module, and native modules break the distroless/Kaniko build for no practical
  gain at course scale. The stored format carries its parameters, so the cost can be raised later
  without invalidating existing rows.
- **D2 — Five runtime dependencies, all pure JS**: `pg`, `ioredis`, `kafkajs`, `jose` (JWT),
  `prom-client`. `node:http` stays — the route table is six entries, and a framework would be the
  only dependency in the tree with an opinion about our code. Hand-rolling JWT was rejected:
  signature verification is exactly the code you do not want to be clever in.
- **D3 — Ports and adapters, so the test stage stays fast.** The pure `handle()` seam survives;
  storage and event publishing become injected interfaces (`Store`, `SessionEvents`). Unit tests
  run against in-memory fakes, so `npm test` still needs no database and the pipeline shape stays
  frozen; the real wiring is proven by the CI smoke and the kind drills.
- **D4 — Redis usage is exactly what the architecture allocates** (§7.1): key
  `session:{sessionId}` (JSON, TTL = token expiry) and channel `session:invalidated:{playerId}`.
  No new prefixes; `ratelimit:*` belongs to the gateway phase.
- **D5 — Schema shaped so the invariant is the database's job.**
  `players(player_id uuid pk, username text, password_hash text, created_at)` with a unique index
  on `lower(username)`; `sessions(session_id uuid pk, player_id fk, is_active, created_at,
  expires_at, invalidated_at, invalidation_reason)` with a **partial unique index on `player_id`
  where `is_active`**. Logins serialize on `SELECT … FROM players … FOR UPDATE` before touching
  `sessions`, so concurrent logins queue rather than collide; the index is the backstop that keeps
  two active sessions impossible regardless. `citext` is avoided deliberately: creating an
  extension needs privileges a per-service role should not have. Architecture §4 also lists
  `email` and `ip_address`; the CLI supplies neither, so they are omitted and recorded as a
  representation-level delta.
- **D6 — Revocation is checked cache-first, database-second.** `whoami` verifies the signature
  locally, then reads `session:{sid}` from Redis; on a miss or a Redis error it falls back to the
  `sessions` row in Postgres (the architecture's "introspection fallback") and repopulates the
  cache. Never fail open — a revoked token must not survive a Redis outage.
- **D7 — Metrics** (`prom-client` defaults plus): `identity_registrations_total`,
  `identity_logins_total{result}`, `identity_sessions_superseded_total`,
  `identity_session_event_publish_failures_total{transport}`,
  `identity_http_request_duration_seconds{route,status}`. The first three are P8's
  business-metric candidates — P8 consolidates dashboards, it does not retrofit instrumentation.
- **D8 — `seed` is client-side**: `register`, and on 409 fall back to `login`, emitting one JSON
  line per account (credentials **and** token, per §5.A). No backend bulk endpoint — nothing else
  would call it, and an unauthenticated bulk-create endpoint is a liability to have running during
  a live demo.
- **D9 — `identity.session-events` declared as a Strimzi `KafkaTopic`** under
  `gitops/platform/kafka/` rather than relying on broker auto-creation, with **3 partitions** and
  3-day retention. The catalog's 64 partitions is a production sizing; on a single-broker kind
  cluster it is noise. Partition count is a values-level change, not a design change.
- **D10 — Sealing-key lifecycle.** One-time: install the controller on a throwaway cluster, back
  the key up (`kubectl -n kube-system get secret -l sealedsecrets.bitnami.com/sealed-secrets-key
  -o yaml > ~/.amicro_sealing_key`). Thereafter `install.sh` applies that Secret **before** the
  controller is applied — a controller that starts first generates its own key and every committed
  blob becomes undecryptable. Missing key file = loud warning, install continues (a platform-only
  drill must still work) and the identity app reports the missing secret.
- **D11 — All sealed material regenerated by one script.** `gitops/secrets/seal.sh` takes the
  operator-held plaintexts and rewrites every sealed file (identity secrets, the DB role password
  in `postgres`, the registry pull secret). It seals **offline** against the certificate extracted
  from the backed-up key, so no cluster is needed; the same plaintext must be sealed once per
  namespace, and doing that by hand at exam time is how secrets drift.
- **D12 — The service app-of-apps becomes Helm-typed**, mirroring what P1 did for the platform:
  one template ranging over a services × environments list in `values.yaml` replaces 20
  byte-identical `Application` files (verified identical modulo the service name). This is what
  makes `targetRevision` cascade to children — and it is also where the `environments` knob lives,
  so a demo cluster registers `staging` only and is green by construction.

## Tooling prerequisite

`kubeseal` and the `argocd` CLI are not installed on this machine. F1 installs both user-mode into
`~/bin` (the pattern `eksctl` already follows), pinned to the versions in the cluster:
sealed-secrets `v0.38.4`, Argo CD `v3.4.5`.

## Risks

- **R1 — Sealing-key custody.** Losing the backup makes every committed SealedSecret dead weight.
  Mitigation: `seal.sh` regenerates everything from plaintext in one command, the recovery
  procedure sits next to the restore code, and the key path is git-ignored. This is the price of
  E1 and it is paid knowingly.
- **R2 — Flipping the `identity` database owner** on a cluster where P1 already created it as
  `app`-owned may not reconcile cleanly. Verified on a fresh kind in F3 first; fallback is to keep
  `app` as owner and grant the `identity` role, which still gives per-service credentials.
- **R3 — Deploy-token creation is a credential action.** F4 stops and asks for explicit
  authorization before creating it (standing convention), and the token is masked in every
  transcript.
- **R4 — kafkajs retry loops** can hold the event loop and delay pod shutdown. Bounded retries,
  lazy connect, and publish failures counted rather than awaited (E7).
- **R5 — CI wall-clock.** The smoke job grows by two pods; if it drifts past the current runtime
  the ephemeral Postgres gets `fsync=off` and smaller resources before anything is dropped.
- **R6 — Route break.** `/register|/login|/whoami` disappear. Both consumers (the CLI and
  `assert-smoke`) live in this repo and change in the same merge; the delta is recorded in
  `CHANGELOG-design.md`. No event or data model is rewritten, so the additive-growth rule holds.
- **R7 — CI minutes and pin ping-pong.** Work happens on `feat/p2-identity-auth`; only
  `services/identity/**`, `clients/cli/**` and `ci/templates/**` create jobs on a branch. Letting
  the digest pin run on the branch means CI pushes a `[skip ci]` commit back to it — every local
  commit after an identity change starts with `git pull --ff-only`. Accepted: it is what makes the
  drills exercise the real pull path instead of a hand-loaded image. One fast-forward merge to
  `main` runs the full pipeline once; spec and docs commits carry `[skip ci]`.
- **R8 — F1 touches every service's Application.** Collapsing 20 files into a template is exactly
  the kind of change that silently drops a service. The gate is a diff of `argocd app list` before
  and after on the same cluster, not a reading of the template.
